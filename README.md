# GophKeeper

Клиент-серверный менеджер приватных данных: пары логин/пароль, произвольный текст,
бинарные файлы и банковские карты. К любой записи можно приложить текстовую
метаинформацию. Данные синхронизируются между несколькими клиентами одного владельца.

Сервер хранит только шифротексты. Мастер-пароль и ключ шифрования никогда не покидают
клиента, поэтому даже полный доступ к базе не раскрывает содержимое записей.

## Архитектура

```
cmd/gophkeeper         CLI-клиент
cmd/gophkeeper-server  gRPC-сервер
internal/crypto        вывод ключей из мастер-пароля, AES-256-GCM
internal/model         доменные типы и сериализация записи
internal/transport     общие лимиты gRPC
internal/server/...    конфигурация, транспорт, бизнес-логика, PostgreSQL
internal/client/...    команды, сценарии, локальное хранилище, вызовы сервера
proto/gophkeeper/v1    контракт и сгенерированный код
```

Клиент и сервер общаются по gRPC поверх TLS — бинарный протокол с описанным
контрактом в `proto/gophkeeper/v1/gophkeeper.proto`. Чтения и вход повторяются
автоматически при недоступности сервера: политика повторов задана в конфигурации
gRPC-соединения, поэтому код вызовов о ней не знает. Отправка изменений не
повторяется — повтор после потерянного ответа столкнул бы клиента с его же
записью как с конфликтом.

## Шифрование

Из мастер-пароля на двух разных солях выводятся два независимых значения:

| Значение | Как получается | Где живёт |
| --- | --- | --- |
| `authKey` | `Argon2id(master, saltAuth)` | уходит на сервер вместо пароля |
| `dataKey` | `Argon2id(master, saltData)` | только в памяти клиента |

Сервер хранит хеш от `authKey`, соли, верификатор и шифротексты. Записи шифруются
AES-256-GCM со свежим случайным nonce; идентификатор записи используется как
дополнительные аутентифицируемые данные, поэтому шифротекст нельзя переставить
между записями. Тип записи, название, поля и метаинформация лежат внутри
шифротекста — снаружи видны только идентификатор, ревизия и отметка об удалении.

Верификатор — зашифрованная на `dataKey` контрольная строка. Клиент расшифровывает
её перед любой операцией, поэтому опечатка в мастер-пароле обнаруживается сразу,
а не в момент, когда прочитать запись уже невозможно.

## Синхронизация

У каждого владельца свой счётчик ревизий: сервер увеличивает его в одной транзакции
с записью секрета. Клиент хранит курсор `lastRevision` и два набора данных — снимок
сервера и очередь собственных изменений.

1. `Pull` отдаёт изменения по возрастанию ревизии; клиент пишет изменение и курсор
   одной транзакцией, поэтому обрыв связи не приводит к пропуску записи.
2. `Push` отправляет накопленные изменения с той ревизией, поверх которой они сделаны.
3. Если запись успели изменить с другого клиента, сервер отвечает `FailedPrecondition`
   и текущей версией. Локальная правка сохраняется, а решение принимает пользователь:

```
gophkeeper sync --resolve local --id <id>    # опубликовать свою версию
gophkeeper sync --resolve remote --id <id>   # отказаться от своей версии
```

Удаление хранится как отметка, иначе второй клиент никогда не узнал бы, что запись
удалили.

## Запуск сервера

```
make cert
createdb gophkeeper
./bin/gophkeeper-server -d "postgres://user:pass@localhost:5432/gophkeeper?sslmode=disable" \
    -k "секрет подписи токенов" -cert server.crt -key server.key
```

Настройки читаются из файла, затем из переменных окружения, затем из флагов —
каждый следующий источник перекрывает предыдущий. Флаги приоритетнее окружения:
флаг задаёт тот, кто запускает процесс сейчас, а переменные приходят из среды
(compose, systemd, CI) и должны перекрываться без её правки.

| Флаг | Переменная | Ключ в JSON | Значение |
| --- | --- | --- | --- |
| `-a` | `GRPC_ADDRESS` | `grpc_address` | адрес сервера, по умолчанию `:3200` |
| `-d` | `DATABASE_URI` | `database_uri` | строка подключения к PostgreSQL |
| `-k` | `JWT_SECRET` | `jwt_secret` | секрет подписи токенов |
| `-cert` | `TLS_CERT` | `cert_file` | сертификат TLS |
| `-key` | `TLS_KEY` | `key_file` | приватный ключ TLS |
| `-c` | `CONFIG` | — | путь к файлу конфигурации |

Файл конфигурации целиком:

```json
{
  "grpc_address": ":3200",
  "database_uri": "postgres://user:pass@localhost:5432/gophkeeper?sslmode=disable",
  "jwt_secret": "секрет подписи токенов",
  "cert_file": "server.crt",
  "key_file": "server.key"
}
```

Схема базы разворачивается миграциями при старте.

## Клиент

Сборка под текущую платформу — `make build`, под все поддерживаемые —
`make build-all` (Linux, macOS, Windows; amd64 и arm64).

```
gophkeeper version
gophkeeper register -l user -a 127.0.0.1:3200 --cacert server.crt
gophkeeper login -l user
gophkeeper add credentials --name bank --login user --meta "интернет-банк"
gophkeeper add text --name note --file note.txt   # без --file текст вводится с клавиатуры
gophkeeper add binary --name archive --file archive.zip
gophkeeper add card --name visa --holder "IVAN IVANOV" --expires 12/29
gophkeeper list
gophkeeper get <id> --out archive.zip
gophkeeper delete <id>
gophkeeper sync
```

Мастер-пароль запрашивается без эха. Для скриптов его можно передать переменной
`GOPHKEEPER_MASTER_PASSWORD`.

Сами секретные значения — пароль записи, текст заметки, номер карты и код проверки —
тоже вводятся без эха и не имеют флагов: аргументы командной строки видны в списке
процессов и остаются в истории оболочки. В скриптах их подают на стандартный ввод
по строке на значение, а текст и бинарные данные можно прочитать из файла (`--file`).

Локальное хранилище — файл `~/.gophkeeper/vault.db` с правами `0600`; путь меняется
флагом `--store`. Записи лежат в нём зашифрованными, поэтому список и просмотр
работают без сети — серверу нужна только команда `sync`.

## Тесты

```
make test
make cover
```

Тесты хранилища работают с настоящей базой и пропускаются, если не задана
переменная `GOPHKEEPER_TEST_DSN`:

```
docker run -d --rm --name gophkeeper-db -e POSTGRES_PASSWORD=keeper -e POSTGRES_USER=keeper \
    -e POSTGRES_DB=keeper -p 55432:5432 postgres:16-alpine
GOPHKEEPER_TEST_DSN="postgres://keeper:keeper@127.0.0.1:55432/keeper?sslmode=disable" make cover
```

Сценарии клиента проверяются на настоящем сервере, поднятом поверх `bufconn`:
регистрация, синхронизация второго клиента, конфликт и его разрешение, передача
бинарных данных потоком.
